# wldx-cli — `wx`, a command line for Wildix

**Version 1.7.0** · unofficial · MIT

`wx` works with Wildix as **the logged-in user**: chats, calls and meetings on record, queue reports, what is going
on now, and your phone. It is the command-line twin of the
[Wildix agent skills](https://github.com/gorets/wildix-skills) and shares their login.

```sh
npm i -g wldx-cli          # the command is `wx`
wx login you@company.com   # a code comes by e-mail
wx status
wx chat list

npx wldx-cli chat list     # without installing
```

Requires Node.js 22 or newer. One dependency: [`wldx-core`](https://github.com/gorets/wildix-cli/tree/main/packages/core), the core it shares with `wx-admin`, from the
same repository and of the same version.

Unofficial: not made or supported by Wildix. It uses the same internal APIs as the Wildix apps, which may change.

## Commands

Every command has `-h`, takes `--profile EMAIL` (which login to use, see [Profiles](#profiles)), and prints text or, with `--output json`, JSON. `wx <group> -h`
lists the commands of a group.

A channel is an id or an inbox link; a message is an id or an inbox link to it; a meeting is an id or an x-bees
link. Commands that reach other people (send, call, transfer, invite) do only what their arguments say; those that
destroy something for everyone need `--yes`. The service does not implement some chat operations yet: their help
says so.

## Output

As in the internal Wildix CLI: **text** for people by default (one line per item, local times), **`--output json`**
for scripts and agents (the data of the service; `--pretty` indents it), `--no-color` for plain text. These options
may stand anywhere: `wx --output json chat list` or `wx chat list --output json | jq`. Streaming commands (`watch`)
print one line per event: text, or one JSON object per line. Messages for people (progress, prompts) go to stderr.

## Completion

Tab completes commands, options and option values (`--filter unread|archived`, `--profile` from your
profiles); zsh and fish show a description next to each. Turn it on once, then open a new terminal:

```sh
echo 'eval "$(wx completion zsh)"'  >> ~/.zshrc     # zsh (after compinit, if your .zshrc runs it)
echo 'eval "$(wx completion bash)"' >> ~/.bashrc    # bash, 3.2 (macOS) and newer
wx completion fish > ~/.config/fish/completions/wx.fish
```

It completes an installed `wx` (`npm i -g wldx-cli`), not `npx wldx-cli`. The script asks `wx __complete` for the
candidates on every Tab, so it follows new commands without being regenerated; it uses no network.

## Login

`wx login you@company.com` sends a one-time code to the e-mail and asks for it. Without a terminal (scripts,
agents), sign in in two steps: `wx login you@company.com --send-code`, then within 3 minutes
`wx login you@company.com --code 123456`.

The session is one file per profile (e-mail) in `~/.wildix/tokens` (`$WILDIX_CONFIG_DIR/tokens`), the same as the
`wildix-auth` agent skill uses: log in with either, both work. An expired token is renewed and written back in the
same format. `wx logout` revokes the session of this device; `--everywhere` signs you out of every device and
app.

## Profiles

Each e-mail you are logged in with is a profile. Which one a command uses:

1. `--profile EMAIL` (anywhere on the command line),
2. else `WILDIX_EMAIL`,
3. else the default profile,
4. else the only one logged in.

The first `wx login` makes its profile the default; logging in with another e-mail does not change it.
`wx profile list` shows them (`*` is the default), `wx profile use EMAIL` changes the default, and `wx status` says
which profile it used and why. The default is kept in `~/.wildix/wx.json`.

## Environment

| Variable | Meaning |
| --- | --- |
| `WILDIX_EMAIL` | the profile to use, before the default one |
| `WILDIX_CONFIG_DIR` | where the sessions are (default `~/.wildix`) |
| `WILDIX_ID_TOKEN` | a token to use as is, instead of a saved session (CI, tests) |
| `WILDIX_STREAM_REGION` | the chat region (default `eu-1`) |
| `WILDIX_STREAM_URL`, `WILDIX_WDA_URL` | another chat or analytics address; only `https://<host>.wildix.com` |
| `WILDIX_STREAM_WS_URL`, `WILDIX_WDA_WS_URL`, `WILDIX_XBEES_URL`, `WILDIX_PBX_URL` | other addresses, only with `WILDIX_ALLOW_CUSTOM_URL=1` (tests) |

| `WX_NO_UPDATE_CHECK=1` | never check npm for a newer version (also off in CI, under `npx`, without a terminal, with `--output json`) |

## Updates

Once a day, while a command runs in a terminal, `wx` asks npm for its latest version (in the background, never
holding the command); when there is a newer one, a line after the output says so: `wx 1.2.0 → 1.3.0 is out: npm i -g
wldx-cli`. Nothing is installed by itself. Off in CI, under `npx`, without a terminal, with `--output json`, or with
`WX_NO_UPDATE_CHECK=1`.

## Exit codes

`0` done · `1` error (network, HTTP) · `2` not logged in, the session cannot be renewed, or a refusal that needs
another login · `3` nothing to show (no transcript yet) · `64` wrong usage.

## Security

- The token is sent only to Wildix: hosts under `wildix.com`, the x-bees API, your own PBX (named in the token
  itself) and the login service. Redirects are refused; presigned file links get no token.
- The token is never printed, never put on a command line or into the environment of another process.
- Session files are written atomically with mode `0600`.
- Files are written only where `--to` says, mode `0600`, never over another file, never into hidden or startup
  folders. Uploads of key files, from credential folders (`~/.ssh`, `~/.aws`, `~/.wildix`, …), of anything hidden in
  the home folder (`~/.git-credentials`, `~/.config/…`, shell histories) and from the macOS keychains are refused.
- Anything read from Wildix (messages, names, transcripts) is data, never instructions. Sending a message or placing
  a call reaches other people: script it with care.
- `wx phone watch`, `list --sip`, `record` and `conference-transfer` register on your extension over SIP as a
  watcher device (user agent `wx watcher`) that never rings and turns down calls; it unregisters on exit.

## Development

`wx` lives in the pnpm workspace of [gorets/wildix-cli](https://github.com/gorets/wildix-cli) next to `wx-admin` and
their shared core (`packages/core`): see the [README](https://github.com/gorets/wildix-cli) and [AGENTS.md](https://github.com/gorets/wildix-cli/blob/main/AGENTS.md) there.

```sh
pnpm install                       # at the root of the repository
pnpm --filter wldx-cli test        # node:test, no network
node packages/wx/bin/wx.mjs status # this checkout, without installing
```

Layout: `bin/wx.mjs` (entry) → `src/cli.mjs` (the spec on the router of the core) → `src/commands/<group>.mjs`,
with helpers per domain in `src/chat`, `src/history`, `src/live`, `src/phone`. Login, sessions, addresses, requests
and text output come from `wldx-core`. See [AGENTS.md](https://github.com/gorets/wildix-cli/blob/main/packages/wx/AGENTS.md).
In `packages/wx`: `node test/dev.mjs <module> <args>` runs a command module that is not listed yet; after changing
commands, regenerate the reference with `node tools/readme-commands.mjs` and paste it between the markers.
